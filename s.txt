Three decisions I locked that the brief left open — flagged here so nobody asks at minute 40:

X-User-Id is the sole source of employee_id on POST /api/requests. No employee_id in the request body. One source of truth, zero mismatch bugs.
The frontend never does date math on created_at. Naive TIMESTAMP strings get parsed as local time by JS and will silently shift the countdown by your UTC offset. The backend ships age_minutes, minutes_remaining, and is_breached precomputed on every request object. FE reads those only.

FILE: SPDD.md
SPDD — Smart Maintenance Request & Escalation System
Codename: SENTINEL · Hospital Critical-Asset Edition · 180-minute build

1. The 30-Second Pitch
In a hospital, a maintenance ticket is not an inconvenience — it is a countdown timer attached to a patient. A ventilator alarm and a broken office chair cannot sit in the same queue with the same urgency.

SENTINEL attaches a life-criticality SLA to every maintenance request at the moment it is created. An ICU ventilator gets 5 minutes. A vaccine fridge gets 10. Office HVAC gets 120. If a request is still open past its SLA, the system escalates it by itself — flips it to Escalated, writes an immutable escalation log, and routes it to the on-call biomedical technician. No human has to remember to chase it.

The wow factor (this is what wins Functionality + Innovation):
Every row in the admin queue has a ⏩ Simulate SLA breach button. The judge clicks it on the ICU ventilator ticket. The row backdates 6 minutes, the next poll lands, and live, on screen: the badge flips amber → red, the row starts pulsing, the countdown goes negative, and a new entry appears in the escalation timeline naming the on-call biomedical tech. Two seconds, no waiting, no faked video.

Why our escalation design beats the obvious one: competitors will reach for a background scheduler (APScheduler / cron / Celery). Schedulers are invisible during a demo, add a dependency, add a failure mode, and cannot be proven to a judge in 2 minutes. We compute escalation on read — it is deterministic, stateless, zero-dependency, and demonstrable on command.

4. Locked Schema (verbatim — copy these names, never rename)

employees

  name          TEXT NOT NULL
  role          TEXT NOT NULL          -- 'employee' | 'admin' | 'technician'

  id            SERIAL PRIMARY KEY

  id            SERIAL PRIMARY KEY
  request_id    INTEGER NOT NULL REFERENCES requests(id)
  from_status   TEXT NOT NULL
  to_status     TEXT NOT NULL
  reason        TEXT NOT NULL
  escalated_to  TEXT
  created_at    TIMESTAMP NOT NULL DEFAULT now()
Three tables. No fourth table. No extra columns. Ever.

5. Pinned Escalation Logic

ESCALATE WHEN:
    status NOT IN ('Resolved', 'Closed', 'Escalated')
    AND (now() - created_at) > sla_minutes
Category	sla_minutes	Escalates to (escalated_to)
Life Support	5	Biomedical On-Call — Suresh Kumar
Oxygen Supply	5	Biomedical On-Call — Suresh Kumar
Cold Chain / Vaccine	10	Facility Admin — Vikram Nair
ER Power	10	Electrical On-Call — Farah Sheikh
IT / Network	60	Facility Admin — Vikram Nair
Facilities / HVAC	120	Facility Admin — Vikram Nair
Idempotency rule — memorize this: Escalated is excluded from the trigger condition. A row that is already Escalated is skipped, so a log row is written exactly once per transition. Without this exclusion every GET appends a duplicate log and the timeline becomes garbage within 30 seconds of the demo.

evaluate_sla(db, rows) runs inside GET /api/requests, GET /api/requests/{id}, POST /api/requests/{id}/age, and GET /api/stats. It lives in exactly one file: escalation.py. Nothing else computes SLA.

6. REST API Contract — complete and final
Base URL: http://localhost:8000
Every request sends: X-User-Id: <int> (from the header switcher) and Content-Type: application/json.
Universal error shape — every non-2xx response, no exceptions:


{ "error": "Request 99 not found" }
6.1 Canonical RequestOut object
Returned by every route that returns a request. Every key present on every response — no conditional keys.


{
  "id": 1,
  "employee_id": 5,
  "employee_name": "Priya Menon",
  "title": "ICU Bed 4 ventilator alarm — low tidal volume",
  "description": "Continuous low tidal volume alarm on Bed 4. Patient is vent-dependent.",
  "category": "Life Support",
  "priority": "Critical",
  "status": "Escalated",
  "sla_minutes": 5,
  "assigned_to": 3,
  "assigned_to_name": "Suresh Kumar",
  "created_at": "2026-08-22T09:12:00",
  "updated_at": "2026-08-22T09:34:11",
  "age_minutes": 22,
  "minutes_remaining": -17,
  "is_breached": true
}
employee_name / assigned_to_name — server-side join. assigned_to and assigned_to_name are null when unassigned.
age_minutes — integer, floor of (now - created_at) in minutes.
minutes_remaining — sla_minutes - age_minutes. Goes negative. FE uses the sign for colour.
is_breached — minutes_remaining < 0 AND status NOT IN ('Resolved','Closed').
Timestamps are naive ISO-8601, no Z, no offset. FE must not parse them for math.

6.3 POST /api/requests
Headers: X-User-Id: 5 — required. This is the employee_id. Do not put employee_id in the body.

Body:

Field	Type	Required	Rule
title	string	yes	non-empty
description	string	no	defaults ""
category	string	yes	must be a key in CATEGORY_SLA
priority	string	no	Low|Medium|High|Critical, default Medium
Server sets: employee_id ← X-User-Id; sla_minutes ← CATEGORY_SLA[category]; status ← Pending; created_at/updated_at ← now().

6.4 GET /api/requests
Runs evaluate_sla() over the result set before serializing. This is where auto-escalation happens.

Query params — all optional, AND-combined:

Param	Example	Meaning
status	?status=Escalated	exact match
category	?category=Life Support	exact match
employee_id	?employee_id=5	requester's own tickets (Employee Dashboard)
assigned_to	?assigned_to=3	technician's queue
Sort order (fixed, non-negotiable): is_breached DESC, then priority (Critical > High > Medium > Low), then created_at ASC. Breached life-support tickets are always row 1. This is a UI/UX mark.

200: [ RequestOut, ... ] — [] when nothing matches (200, never 404).

6.7 PATCH /api/requests/{id}/status
Body:


{ "status": "In Progress" }
Allowed: Pending | In Progress | Resolved | Escalated | Closed.

Side effects:

always sets updated_at = now()
status == "Escalated" (manual flag) → writes an escalation_logs row: reason = "Manual escalation by <name of X-User-Id>", escalated_to = ESCALATION_TARGET[category]
Resolved / Closed → row permanently exits SLA evaluation
200: RequestOut
400: {"error": "Invalid status 'Done'. Allowed: Pending, In Progress, Resolved, Escalated, Closed"}
404: {"error": "Request 99 not found"}

6.8 PATCH /api/requests/{id}/assign
Body:


{ "assigned_to": 3 }
null unassigns.

Side effect (Innovation mark): if current status == "Pending" and assigned_to is not null, status auto-bumps to In Progress. Assigning is acknowledging — one click instead of two.

200: RequestOut
404: {"error": "Request 99 not found"} or {"error": "Employee 99 not found"}
400: {"error": "assigned_to must reference an employee with role technician or admin"}

6.10 GET /api/stats
Runs evaluate_sla() across all open rows first, so the cards are never stale.

200:


{
  "total": 12,
  "pending": 4,
  "in_progress": 3,
  "resolved": 3,
  "escalated": 2,
  "critical_open": 3,
  "breached_open": 2,
  "breach_rate_pct": 16.7
}
critical_open = priority == 'Critical' AND status NOT IN ('Resolved','Closed').
breach_rate_pct = round(escalated / total * 100, 1); 0.0 when total == 0.

6.11 Status-code summary
Code	Used for
200	successful GET / PATCH / age
201	request created
400	bad header, bad enum value, bad query param
404	request or employee id not found
422	Pydantic body validation failure (reshaped to {"error": ...})
500	anything unexpected — {"error": "Internal server error"}
